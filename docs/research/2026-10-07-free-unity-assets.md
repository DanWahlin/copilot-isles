## 3. Licensing summary (Unity Asset Store Standard EULA)

Source: [Asset Store Terms of Service + EULA (Appendix 1)](https://unity.com/legal/as-terms), last updated Dec 4, 2024.

**Use outside the Unity engine (in a web/three.js game):** The EULA is **engine-agnostic**. §2.2.1 grants a license to:
> "(a) incorporate the Asset, together with substantial, original content not obtained through the Unity Asset Store, into an electronic application or digital media that has a purpose, features, and functions beyond the display... of Assets ("Licensed Product") as an embedded component of that Licensed Product, such that the Asset does not comprise a substantial portion of the Licensed Product; (b) reproduce, publicly display... distribute the Asset as incorporated and embedded in that Licensed Product."

Nothing requires the "Licensed Product" to be built with Unity. Converting FBX→glTF and using the mesh/texture data inside your three.js game is squarely "incorporating the Asset... into digital media... as an embedded component," which is permitted — **as long as your game is substantial original work and these assets are not the only/primary content** (true here — you already have a large original codebase and many CC0 sources).

**Redistribution of source files / public repo risk:** This is the real constraint. §2.2.1.1(d) prohibits:
> "use, reproduce, duplicate, publicly display, publicly perform, copy, modify, adapt, translate, prepare derivative works of, distribute, transfer, license, sublicense... any Asset except as expressly permitted in this EULA,"

and the base Terms §3.5 similarly forbid redistributing the Asset itself outside the Licensed Product. **Practical reading:** shipping converted `.glb`/texture files *embedded in your compiled/served game* is fine (that's the permitted "incorporated and embedded" distribution); but committing the **raw converted asset files to a public GitHub repository** — where anyone can clone the repo and lift out standalone `.glb`/texture files — is much closer to "redistributing the Asset" outside the Licensed Product and is legally riskier once the repo goes public. Recommendation: if/when the repo is made public, either (a) keep converted third-party Unity-asset files in a private submodule/LFS store pulled at build time and not committed to the public tree, or (b) replace any Unity Asset Store-derived assets with CC0 equivalents before making the repo public, or (c) obtain direct permission from the publisher.

**Restricted/non-standard terms found in this batch:** None of the verified assets above were marked "Restricted Asset" or "Extension Asset" (those categories — SDKs/editor tools/scripting — carry per-seat and different redistribution terms per §2.2.2/§2.3.2, not relevant to 3D/audio assets here). All checked assets used the plain Standard EULA; no custom publisher EULA banners were observed on these pages. None were flagged CC‑BY/attribution-only or "personal use only" — if a publisher does attach such terms, the Store displays a separate "Restricted Asset Terms" link on the page, which none of the fetched pages showed.

**AI/ML clause:** §3.8(v)/§2.2.1.1(g) forbid using Store assets "for purposes such as training an artificial intelligence or machine learning model" — irrelevant to this project (you're using them as 3D content, not training data) but worth knowing it exists.

## 4. Conversion pipeline summary (Unity package → three.js)

1. **Extracting `.unitypackage` without Unity:** Confirmed feasible — a `.unitypackage` is just a gzipped tar archive. `tar -xzf Thing.unitypackage` yields a folder tree of GUID-named folders, each containing an `asset` (the actual binary, e.g. FBX/PNG), `asset.meta` (Unity's import metadata), and a `pathname` file telling you the asset's original project-relative path. Reconstruct a sane folder by reading each `pathname` file and copying `asset` to that path. No Unity install required.
2. **FBX → glTF:** Use Blender's built-in FBX importer, then `File → Export → glTF 2.0`, or the standalone `FBX2glTF` CLI for a scriptable/batch pipeline. Blender is generally preferred because it lets you inspect/fix geometry (flip normals, fix non-manifold meshes, delete hidden faces) and re-bake materials before export — matches your existing Blender + gltf-transform pipeline.
3. **Rebuilding materials:** Unity Standard/URP Lit shader maps (Albedo, Metallic/Smoothness, Normal, Occlusion) map fairly directly onto glTF's `pbrMetallicRoughness` — Blender's glTF exporter handles this if you wire the Principled BSDF correctly. For hand-painted/toon-ish stylized assets (unlit-looking, baked lighting in the diffuse texture), set `roughness` high (~0.8–1) and `metalness` to 0, and consider authoring a custom TSL toon/cel node for WebGPU rather than fighting PBR response — this matches how your Quaternius/Kenney assets are likely already handled.
4. **Prefabs/lightmaps:** Not portable — Unity prefab hierarchies, baked lightmap UV2 data, and lightmap textures are Unity-internal and must be discarded; re-author any multi-mesh assemblies as groups directly in Blender/three.js and re-bake AO/lighting into your own atlas pipeline if needed.
5. **Animations:** FBX animation clips (skeletal/vertex) export to glTF natively via Blender and work fine in three.js's `AnimationMixer` — this applies to the "Creative Characters" and "FREE Low Poly Human RPG" packs' walk/idle/combat clips. **Mecanim humanoid retargeting (Avatar masks, IK, Animator Controller state graphs) is Unity-only and does not transfer** — you only get the raw baked clips, not the retargeting system, so each character's clips must already be authored on a compatible rig or re-targeted manually in Blender (e.g., via Rokoko/Auto-Rig Pro) before export.
6. **VFX packages:** The Unity ParticleSystem components (emission shape, curves, sub-emitters) are not portable at all. Only the flipbook sprite-sheet **textures** (e.g., Maiami Studio's smoke, SOLODREAM's flame) transfer — extract the PNG/texture, then build the actual particle behavior natively in your three.js/TSL particle system.
7. Run everything through **gltf-transform** afterward for your existing optimization pass (dedup, texture compression/KTX2, prune, draco/meshopt) exactly as you do for the Quaternius/Kenney assets today — these Unity-sourced meshes are typically *higher* poly than your existing kits, so expect to run decimation/retopology in Blender before export to hold to your iPad budget.

## 5. CC0 alternatives worth considering instead

Given your repo's stated preference for CC0 so it survives going public, and the licensing ambiguity above, these are lower-risk substitutes for the same gaps:

- **Pirate ship/boat hull** (nothing free on Unity Store) → Quaternius "Pirate Kit" (already in your stack) or Poly Pizza pirate/ship models — both CC0.
- **Castle/fortress pieces** (nothing free on Unity Store) → Quaternius "Medieval Village MegaKit" (already in your stack, likely already has keep/tower pieces) or Kenney's castle kit if one exists.
- **Seagulls/dolphins/fish** (nothing free on Unity Store) → Poly Pizza or Kenney animal packs, or Quaternius's animal kits — check for CC0 bird/sea-creature models there first.
- **Ocean/wind/gull/cannon/creak ambience** (no themed free bundle found on Unity Store) → Freesound.org (filter for CC0) or Kenney's free audio packs (explicitly CC0, matches your existing Kenney RPG audio) — much cleaner for a public repo than re-exporting Unity Store `.wav` files whose EULA redistribution terms are the same ambiguity as the 3D assets.
- **Palm trees/tropical vegetation** — your existing Quaternius "Stylized Nature MegaKit" almost certainly already has better-integrated, consistent-style palms than Sara Bellio's sample pack (which has a materials complaint in reviews); use the Unity Store palm pack only as a supplementary variant, not a replacement.
- **Skyboxes** — since these are large single images, not meshes, the EULA redistribution risk is the same, but low practical risk (a skybox image isn't really a "component" people extract and reuse elsewhere); still, if going public matters a lot, equirectangular HDRIs from Poly Haven (CC0) are a strictly safer choice for the same purpose.
